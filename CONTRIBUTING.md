# Contributing

How work happens in this repository. The reasons behind these rules are in [ADR 0013](docs/adr/0013-pull-request-workflow.md); the assistant-specific rules are in the [assistant working guide](docs/ASSISTANT_WORKING_GUIDE.md).

## Decisions

The owner makes every decision. Options, trade-offs, and a recommendation come first; building waits for the choice. Material decisions get an ADR in [`docs/adr/`](docs/adr/README.md); smaller ones are written into the relevant spec.

## How a chunk of work flows

1. **Design.** Types, function signatures, and the planned tests, with options where there's a real choice. The owner approves or changes it.
2. **Build** on a feature branch, one concept per PR.
3. **Verify.** Run the local checks below and record the actual output.
4. **Explain back.** The owner explains the design and why in a few sentences; gaps get discussed before merging.
5. **Review and merge.** CI must pass; the owner squash-merges.

Each phase starts with a short reading assignment and ends with a learning note in [`docs/learning/`](docs/learning/README.md).

## Working copies

- **Owner:** a clone on the WSL ext4 filesystem (`~/src/agent-platform-foundation`). Integration tests and evals that need Ollama run here.
- **Assistant:** the Windows-side folder, fetched by the owner's clone as the git remote `assistant`.

The owner pushes branches to GitHub and opens PRs.

## Branches

`type/short-topic`, using the commit types below, e.g. `feat/run-state-machine`, `docs/observability-spec`, `ci/hardening`. Never commit directly to `master`; it is protected.

## Commits and PR titles

[Conventional Commits](https://www.conventionalcommits.org/): `type: imperative summary`, lower case, no full stop.

| Type | For |
|---|---|
| `feat` | New behaviour |
| `fix` | A bug fix |
| `test` | Tests only |
| `refactor` | Restructuring without behaviour change |
| `perf` | Performance |
| `docs` | Documentation only |
| `build` | Packaging, dependencies, toolchain |
| `ci` | CI configuration |
| `chore` | Anything else |

PRs are squash-merged, so the **PR title becomes the commit on `master`** and must follow the same format. The `pr title` check enforces it, because release-please builds the version and changelog from these commits.

## Pull requests

- One concept per PR, about 300 changed lines at most (lockfiles excluded). Larger work becomes a series of PRs.
- Fill in every section of the template, briefly and verb-led. Design reasoning lives in ADRs, chat, and learning notes, not in PR descriptions.
- No AI attribution anywhere: no `Co-Authored-By` trailers, session links, or "generated by" lines.
- The required checks must pass before merging: `lint, types, tests`, `audit`, `pr title`, and `zizmor` ([ADR 0021](docs/adr/0021-supply-chain-and-releases.md)).

## Local checks

```bash
uv sync                          # Python 3.15 and dev tools, exactly as locked
uv run pre-commit install        # once per clone: Ruff runs on every commit
uv run ruff format --check .
uv run ruff check .
uv run pyright
uv run pytest
```

The pre-commit hook runs only Ruff, to keep commits fast. Pyright and tests run in CI and whenever you run them yourself.

## Dependencies

- Add or upgrade with `uv add` / `uv lock --upgrade-package`, and commit `uv.lock` in the same PR.
- uv won't resolve any release younger than 7 days (`exclude-newer` in `pyproject.toml`). For an urgent security fix, add a per-package `exclude-newer-package` override and say why in the PR.
- Dependabot opens grouped PRs weekly for GitHub Actions and Python. Review them like any other PR.
- If `audit` reports a vulnerability with no fix available, ignore it by ID (`--ignore-until-fixed`) in `ci.yml`, with the reason in the PR.

## Releases

release-please keeps a release PR open on `master` with the next version and changelog. Merge it only at the end of a milestone. Merging creates the tag and GitHub release, and the workflow attaches an SBOM. Never edit versions or `CHANGELOG.md` by hand.

One-time setup, done by the owner:

1. Create a GitHub App (owner account, not public), with repository permissions Contents, Pull requests, and Issues set to read and write, and no webhook. Install it on this repository only.
2. Create an environment named `release` with deployment branches limited to `master`.
3. In that environment, add the App's client ID as the variable `RELEASE_APP_CLIENT_ID` and a generated private key as the secret `RELEASE_APP_PRIVATE_KEY`. Then delete the downloaded key file.

The repository setting that lets `GITHUB_TOKEN` create pull requests stays off; release-please uses the App's token instead.

## Never commit

Secrets or `.env` files, personal files, private eval sets (`evals/private/`), model weights, database volumes, local paths, or usernames. The repository is public.

## Postmortems

After a notable failure (a real bug, a bad eval regression, a process mistake), the assistant may suggest a one-page blameless postmortem in `docs/postmortems/`: what happened, impact, root cause, what changes. The owner decides whether to write one.
